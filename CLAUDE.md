# kalidoku — règles projet pour assistants IA

> Ce fichier est la **source de vérité** pour tout assistant IA qui contribue au projet (Claude Code, Codex, Copilot, agents custom). Lis-le **en entier** avant le moindre commit.

## 1. Identité du projet

- **Nom** : `kalidoku`
- **Repo** : `github.com/Calixteair/kalidoku` (public, AGPL-3.0)
- **Domaine prod** : `kalidoku.calixteair.fr`
- **Stack VPS hôte** : `calixteair.fr` (Debian 11, Docker Compose, NPM, OpenBao, Wazuh)

## 2. Règles de commit non négociables

### Conventional Commits, messages courts

Format : `<type>(<scope>?): <sujet 50 chars max>`

Types autorisés : `feat`, `fix`, `chore`, `docs`, `refactor`, `test`, `ci`, `perf`, `build`, `style`.

Scopes courants : `core`, `server`, `worker`, `web`, `infra`, `domain-paris-metro`, `auth`, `bao`.

Exemples valides :
```
feat(core): add ends_with predicate
fix(server): reject empty answer in /play
ci: cache cargo target between runs
```

### Interdictions strictes

- **Aucune mention** de Claude, Anthropic, Copilot, Codex, GPT, IA, AI, "generated by", "co-authored by Claude", etc. dans :
  - les messages de commit
  - les corps de PR
  - les release notes
  - le code source (commentaires inclus)
  - les fichiers de doc
- **Pas de `Co-Authored-By:` automatique**. Les co-authors sont uniquement des humains réels qui ont effectivement contribué.
- **Pas d'emojis** dans les commits, PR, code, ou docs sauf si explicitement demandé.
- **Pas de `--no-verify`**, `--force-push` sur `main`, `--amend` sur des commits déjà pushés.

### Branch / PR

- Branche `main` protégée : pas de push direct, PR obligatoire, CI verte requise.
- Branches feature : `feat/<short-slug>`, `fix/<short-slug>`, `chore/<short-slug>`.
- 1 reviewer requis (auto-review accepté quand on est seul, mais relire vraiment).
- Squash merge par défaut.

## 3. Architecture

```
kalidoku/
├── core/              ← lib Rust pure (pas d'I/O, pas d'async)
├── server/            ← backend Axum (API HTTP)
├── worker/            ← générateur de grilles (cron + à la demande)
├── web/               ← frontend Astro + Svelte 5
├── domains/           ← domain packs (paris-metro, etc.)
├── contracts/         ← JSON Schema entités, OpenAPI v1
├── infra/             ← Dockerfiles, docker-compose, configs Bao, scripts ops
├── docs/              ← doc humaine (architecture, agents, sécurité)
├── scripts/           ← scripts dev (ingest, fmt, etc.)
└── .github/           ← workflows CI/CD, templates
```

### Règles d'architecture

- **`core/` ne dépend de rien** sauf serde. Pas d'async, pas de DB, pas de HTTP. Pure logique métier.
- **`server/` et `worker/` dépendent de `core/`**, jamais l'inverse.
- **Le moteur ignore le métier** : ajouter un domaine = ajouter un dossier dans `domains/`, jamais toucher à `core/`.
- **Toute interaction DB passe par SeaORM** avec entities générées (`sea-orm-cli generate entity`).
- **OpenAPI v1 (`contracts/openapi.yaml`) est la source de vérité** du contrat front/back. Régénérer le client TS depuis ce fichier, pas l'inverse.
- **Mobile-first impératif** : design conçu pour 360px d'abord, breakpoints `md:` et `lg:` enrichissent sans réorganiser.
- **PWA + Capacitor-ready** : pas de dépendance web-only sans équivalent Capacitor.

## 4. Sécurité

### Secrets

- **Jamais de secret en clair** dans le code, les commits, les `.env` versionnés, les fichiers `.md`, les logs ou les messages.
- Tous les secrets runtime passent par **OpenBao** (`secrets.calixteair.fr`) via `bao-agent` systemd, pattern Option B.
- Path KV : `secret/kalidoku/prod/{db,backend,oidc}` + secret partagé `secret/_shared/smtp` si besoin.
- Secrets CI dans GitHub Secrets uniquement (`DEPLOY_SSH_KEY`, `DOCKERHUB_TOKEN`, etc.). Jamais dans Bao (CI ↔ Bao = pas de pont sauf via OIDC GHA).
- **Charset DB password** : alphanumeric uniquement (`a-zA-Z0-9`). Pas de `$`, `:`, `&`, `*`, `#`. Voir gotchas Wazuh dans wiki `[[vps-wazuh-deployment-phase1]]`.
- **`kv patch` toujours, jamais `kv put`** pour ajouter une variable dans un secret existant.

### Pre-commit obligatoires (locaux)

- `cargo fmt --check`
- `cargo clippy --all-targets --all-features -- -D warnings`
- `cargo test`
- `pnpm typecheck` côté `web/`
- `pnpm lint`
- `gitleaks protect --staged`

Si un hook bloque, **diagnostiquer et fixer**, jamais bypasser avec `--no-verify`.

### CI obligatoire

- `cargo fmt`, `cargo clippy -D warnings`, `cargo test`, `pnpm typecheck`, `pnpm lint`, `pnpm test`.
- **Trivy** scan de l'image Docker, **CRITICAL bloque** la PR.
- **`gitleaks` full-scan** sur la PR.
- Snyk **n'est pas en CI** — lancé manuellement avant chaque release v*.

### Headers HTTP côté backend (production)

- `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`
- `Content-Security-Policy` strict (default-src 'self', nonce sur scripts inline)
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy` minimal

### Cookies de session

- `__Host-session`, `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/` — Lax (et non Strict) car le callback OIDC est un redirect cross-site depuis Keycloak ; Strict empêcherait l'envoi du cookie fraîchement posé sur la première navigation retour. CSRF couvert par `__Host-` + Secure + HttpOnly + play-token HMAC lié au device.
- Token = 32 bytes random base64. **Stocker le hash SHA-256 en DB**, jamais le clair.

### Auth

- **Keycloak** (`auth.calixteair.fr`) en source de vérité, realm `kalidoku`.
- Flow : Authorization Code + PKCE.
- Backend valide le JWT via JWKS Keycloak.
- Identity providers Keycloak : Google + Discord. Email/password local en backup.
- Pas de stockage password côté kalidoku.

### Anti-bot / anti-scraping

- **Altcha** invisible PoW (proof-of-work) sur inscription Keycloak et démarrage de partie en cas de pic suspect. Self-hosted, pas de service tiers, RGPD friendly. SPI Keycloak réutilisé depuis DSV (cf. wiki `[[devsecvault-altcha-spi]]`).
- Rate limit `tower_governor` : 1 req/250ms par device, 60 req/min par IP.
- `play_token` HMAC court (TTL 1h) requis pour chaque `POST /play`, lié à `device_id + grid_id`.
- Solutions **jamais envoyées au client** avant fin de partie.
- IDs opaques (UUID, jamais d'auto-increment exposé).

## 5. CI/CD

### Pipeline (commit → prod)

```
push → CI: lint + test + trivy → build multi-arch (amd64) → push Docker Hub
                                                                    │
                                                                    ▼
                                                        deploy.yml SSH ci-kalidoku
                                                                    │
                                                                    ▼
                                                        bao-deploy.sh kalidoku
                                                                    │
                                                                    ▼
                                                        docker compose up -d
```

### Tags Docker Hub

- `calixteair/kalidoku-server:latest` → main
- `calixteair/kalidoku-server:sha-<7 chars>` → immutable par commit
- `calixteair/kalidoku-server:vMAJ.MIN.PATCH` → release tag
- Idem pour `kalidoku-worker` et `kalidoku-web`.

### Releases

- `release-please` génère PR de release auto sur push main.
- Merge de la PR de release → tag `vX.Y.Z` + GitHub Release + changelog auto.

## 6. Frontend (web/)

- **Astro 4** pour le routing/pages, **Svelte 5** pour les îlots interactifs.
- **TypeScript strict**.
- **Tailwind 4** + `shadcn-svelte` pour les composants UI + `lucide-svelte` pour les icônes.
- **paraglide-js (Inlang)** pour i18n FR/EN.
- **Mobile-first strict** : pas de breakpoint en dessous de 360px. `sm:`/`md:`/`lg:` enrichissent.
- **Capacitor-ready** : éviter les API web sans pendant Capacitor (Geolocation native OK, Web Bluetooth non).
- **PWA** : manifest + service worker, offline cache de la grille du jour.
- **Accessibilité WCAG 2.1 AA** : tests axe-core dans Playwright.

## 7. Backend (server/)

- **Axum 0.7+**, Tokio multi-thread.
- **SeaORM** pour la DB (Postgres 16). Entities générées via `sea-orm-cli`.
- **`tracing`** + `tracing-subscriber` JSON pour logs.
- **`tower_governor`** pour rate limit.
- **`jsonwebtoken`** + `reqwest` directs pour validation JWT Keycloak (PKCE + JWKS handshake écrits à la main dans `server/src/auth/`).
- **Migrations versionnées** dans `server/migrations/`.
- **Les handlers ne contiennent pas de logique métier** : ils délèguent à `core/` ou à des services dans `server/src/services/`.

## 8. Worker (worker/)

- Binaire séparé qui partage `core/`.
- Cron interne (`tokio-cron-scheduler`) ou trigger HTTP du server.
- Génère les grilles `daily` toutes les nuits + grilles `solo` à la demande (queue Redis).
- **Idempotent** : ne regénère pas si la grille du jour existe déjà pour `(domain, date)`.

## 9. Standards de code (rappel global)

Après toute implémentation, vérifier :

- Fonction > 30 lignes → probablement trop de responsabilités, découper.
- Logique dupliquée > 2 fois → extraire une utilitaire.
- `any` TypeScript ou `unwrap()` Rust gratuit → remplacer par un type/Result réel.
- Composant Svelte > 3 props liées → regrouper en objet.
- Opération async sans gestion d'erreur → ajouter.

## 10. Logging

- **Backend Rust** : `tracing` JSON sur stdout.
- **Frontend** : pas de `console.log` en prod (lint le bloque).
- Logs Docker stdout JSON → captés par l'agent Wazuh host (`/var/lib/docker/containers/*/*.log`).
- Pas de log de PII (mots de passe, tokens, emails complets). Tronquer/hasher si besoin.

## 11. Process

- Toute nouvelle feature = issue GitHub d'abord (template fourni).
- Toute PR = checklist de la PR template remplie.
- Toute migration de DB = NUMERO ascendant + non destructive (idempotente, additive).
- Toute breaking change API = bump version OpenAPI + changelog + deprecation period.

## 12. Gestion des secrets via Bao (procédure type)

Voir wiki `[[vps-chantier-bao-migration]]` et `[[lab-openbao]]`.

### Push d'un nouveau secret

```bash
ROOT_TOKEN=$(jq -r .root_token ~/.config/openbao/init-secrets.json)
ssh vps-claude "sudo docker exec -e BAO_TOKEN=$ROOT_TOKEN openbao bao kv patch secret/kalidoku/prod/<sub> NEW_VAR='valeur'"
```

### Re-wrap secret_id avant restart bao-agent

```bash
ssh vps-claude "sudo bash -c '
  WRAP=\$(docker exec -e BAO_TOKEN=$ROOT_TOKEN openbao bao write -wrap-ttl=10m -force -field=wrapping_token auth/approle/role/kalidoku-prod/secret-id)
  echo \"\$WRAP\" > /etc/bao/kalidoku/secret_id_wrap
  chmod 600 /etc/bao/kalidoku/secret_id_wrap
  systemctl restart bao-agent@kalidoku.service
'"
```

### Redéploiement

```bash
ssh vps-claude "sudo /usr/local/sbin/bao-deploy.sh kalidoku"
```

## 13. Pour les agents IA en parallèle

Voir `docs/agents/` :

- Agent A — `core/` (Rust pur)
- Agent B — `worker/`
- Agent C — `server/`
- Agent D — `web/`
- Agent E — `infra/` + CI
- Agent F — `domains/paris-metro/` (ingest dataset)

**Règles de coexistence** :

- Chaque agent **respecte son périmètre** (le dossier indiqué + ses tests).
- Chaque agent **lit `contracts/`** avant de toucher à un type partagé.
- **Toute modification d'un contrat** (`contracts/entity-schema.json`, `contracts/openapi.yaml`) = PR dédiée + ping des autres agents.
- **Pas de touch-and-go cross-périmètre** sans coordination.
